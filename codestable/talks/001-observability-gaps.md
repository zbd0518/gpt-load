# GPT-Load 的观测外围缺口 talk

> 状态：未定议题。本文记录"缺口是怎么被发现的"，不是实现计划。

---

## 1. 起头是"对比另一个工程"

用户要求把本仓与 `E:\workspace\goland\octopus` 做对比。第一轮比的是**架构**：配置如何生效（不可变快照 Publish vs 写库刷缓存）、调度怎么选（scheduler 迭代器 vs relay/balancer）、执行适配（Bifrost/CLIProxyAPI vs 单一 relay）。

**已查明：** octopus 已宣布 `v2.7.3-Fix2` 为最终版本、停止维护，作者称转向新网关。这意味着它只能当**参照实现**，不能当长期依赖。

## 2. 关注点被收窄成"功能差异"

用户明确要的是功能而不是架构，于是改按管理面路由表、`internal/` 包结构和两边 README 做功能矩阵。

**已查明（事实，非决策）：**
- gpt-load **没有**：告警规则、通知渠道、计划报表、用户/角色、全局模型映射规则、自建缓存、插件、云备份。
- octopus **没有**：WebRTC/实时通话、订阅渠道 OAuth 分期授权与授权态机、凭据级配额观测、请求脱敏与恢复。
- 重叠区大致是：多渠道/多 Key、协议互转、调度重试、Key 治理、价格与用量、请求日志、代理配置。

结论一句话：**octopus 宽，gpt-load 深，重叠约 40%。**

## 3. 由此浮出三个候选缺口

按"对现有结构冲击从小到大"排序，这是我看出的三个真正值得讨论的缺口：

**(a) 观测外围：告警 + 通知 + 报表**
- 现状：gpt-load 只有请求日志、用量统计、`/health` 和更新检查；出问题要人主动去看。
- 参照：octopus `internal/server/handlers/alert.go`、`notification.go`、`report.go`，告警规则含作用域 + 滑动窗口 + 多通知渠道。
- 接入难点：gpt-load 的运行时数据在内存注册表 + 快照里，告警扫描要接到 `control.Runtime` 的后台循环，且不能阻塞数据面。
- 候选质量（非承诺）：告警误报率、通知送达可靠性、扫描对数据面延迟的影响。

**(b) 多用户与 RBAC**
- 现状：管理面单 `AUTH_KEY`（`internal/control/auth.go`），拿到即全权。
- 判断：这不是"加一条路由"能解决的——审计、幂等、写锁都围绕单主体设计。**要做得先改鉴权与审计模型**，成本远高于 (a)。
- 候选质量：最小权限、越权访问、审计完整性。

**(c) 全局模型映射（exact/wildcard/regex + 优先级 + 分组作用域）**
- 现状：gpt-load 只有分组内 alias 与上游侧改写（`dialect/model_rewrite.go`）。
- 参照：octopus `internal/model/model_mapping.go`，实现量小，但解决"上游模型名与客户端不一致"这个高频痛点。
- 候选质量：正则误匹配、规则冲突时的优先级可解释性。

## 4. 边界：本轮不做

- 没有确认要做任何一项，也没有排优先级；三项都还只是候选。
- 没有讨论具体阈值口径（错误率窗口、费用阈值粒度）。
- 没有讨论是否把某一项升级为 Epic。

## 仍开放

1. 三项里先做哪一项？我的推荐是 (c) → (a) → (b)：收益/成本比最好的是模型映射，其次是观测外围；RBAC 最贵且会动鉴权地基。
2. (a) 的通知渠道要几种起步？（octopus 是 8 种，但个人场景 Telegram/Webhook 往往就够）
3. 告警数据从请求日志现算，还是单独维护滚动窗口指标？前者省事、后者才准。
